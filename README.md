# Casino Project

Навчальний веб-проєкт казино на Spring Boot 4: Thymeleaf-сторінки, REST API зі Swagger, JPA і JDBC поверх PostgreSQL (Supabase), Spring Security, псевдо-платіжна система і три гри. Гроші несправжні.

## Запуск

Потрібні Java 25 і доступ до бази PostgreSQL. Параметри підключення беруться зі змінних середовища `SUPABASE_DB_URL`, `SUPABASE_DB_USERNAME`, `SUPABASE_DB_PASSWORD`. Їх можна задати в IntelliJ (вони там вже є в конфігурації запуску) або просто покласти у файл `.env` у корені проєкту, він підхоплюється автоматично. Приклад усіх змінних лежить у `.env.example`.

Запуск командою `./mvnw spring-boot:run`, після чого сайт відкривається на http://localhost:8082, а Swagger UI на http://localhost:8082/swagger-ui.html. При першому старті Flyway застосує міграції V1 і V2 (V2 додає платежі, банк казино, тип гри CRYPTO і стартові ігри з промокодами), а `DataInitializer` створить адміністратора з логіном і паролем із `CASINO_ADMIN_USERNAME` / `CASINO_ADMIN_PASSWORD` (за замовчуванням admin / admin12345, краще змінити).

Тест `CasinoProjectApplicationTests` піднімає весь контекст і тому потребує доступної бази. `GameLogicTest` перевіряє математику ігор і шифрування без бази.

## Як це працює

Гравець реєструється, поповнює баланс тестовою карткою на сторінці гаманця і грає. Картка `4242 4242 4242 4242` проходить завжди, картки що закінчуються на `0002` відхиляються шлюзом, а на `0119` шлюз імітує збій. Термін дії будь-який у майбутньому, CVV будь-які три цифри. Також можна активувати промокод `WELCOME50` або `FRIDAY10`.

Платіжний шлюз (`FakePaymentGateway`) нікуди гроші не відправляє, але поводиться як справжній: перевіряє картку, може відмовити або впасти, і підписує кожну відповідь HMAC-SHA256. `PaymentService` перевіряє цей підпис перед тим, як нарахувати гроші. Номер картки зберігається в базі тільки зашифрованим AES-256-GCM (ключ у `CASINO_ENCRYPTION_KEY`), для показу є маска, CVV не зберігається взагалі. Паролі зберігаються як BCrypt-хеш. Виведення коштів зроблене однією транзакцією: якщо шлюз відмовив, списання з балансу відкочується.

Кожна ставка йде через `PlayService`: гроші списуються з гравця і потрапляють у банк казино (таблиця `house_bank`), потім движок гри рахує результат, і виграш виплачується з банку. Усі рухи грошей пишуться в журнал `transactions`.

## Захист банку

`HouseGuard` рахує максимальний чистий виграш за одну ставку: це менше з двох значень, 5% від поточного банку казино і 5000 (налаштовується в `application.properties` через `casino.house.*`). Якщо випадковий результат дав би більший виграш, движок гри тихо підмінює його на програшний. У слотах барабани перекручуються, у кубику число переноситься в програшну зону, а в крипто-грі монета обвалюється рівно в той момент, коли продаж дав би забагато. Банк можна поповнити з адмінки, і чим він більший, тим більші виграші можуть випадати.

## Ігри

Crypto Trader. Гравець купує монету на суму ставки, і ціна змінюється кожні 300 мс. Продати можна будь-коли, виплата дорівнює ставці помноженій на поточну ціну мінус 3% комісії. Ціна рухається випадково з невеликим нахилом вниз, і на кожному тіку є шанс обвалу, після якого ставка згорає. Весь графік генерується на сервері заздалегідь, але клієнту віддаються тільки ціни до поточного моменту, тому підглянути майбутнє неможливо. Комісія, нахил і обвали разом дають казино перевагу при будь-якій стратегії: часто можна трохи виграти, але на дистанції гравець втрачає (за симуляцією віддача від 45% до 80% залежно від того, як рано продавати).

Lucky Slots. Три барабани з символами різної ваги. Три однакові платять від x5 (вишні) до x300 (сімки), дві вишні повертають x1.5. Віддача приблизно 87%.

Dice 100. Гравець обирає шанс від 2 до 95 відсотків, множник рахується як 96 / шанс. Віддача 96% при будь-якому шансі.

## Що де лежить (відповідність лабораторним)

Лаба 2 (біни і DI). Компоненти через `@Component`, `@Service`, `@Repository`, `@Controller`. Біни через `@Bean` в `AppConfig`: `SecureRandom` як singleton і `PricePathGenerator` як prototype (кожен крипто-раунд отримує новий екземпляр через `ObjectProvider`). Ін'єкція через конструктор використовується майже скрізь, через сетер у `WalletService.setTransactionDao`, напряму в поле в `GlobalModelAdvice`.

Лаба 3 (Thymeleaf). Сторінки в `templates`. Умови `th:if` / `th:unless` і оператор Elvis `?:` є у шапці, гаманці і сторінці помилки, `th:switch` в іконках ігор на головній і в статусах на сторінці історії, `th:each` у всіх таблицях. Весь вивід іде через `th:text`, тому HTML екранується, додатково увімкнено Content-Security-Policy, а форми захищені CSRF-токеном.

Лаба 4 (REST). Повний CRUD для `/api/games`, там же фільтрація по type, active, name з пагінацією і сортуванням, і часткове оновлення через JSON Merge Patch (`application/merge-patch+json`, RFC 7386) та JSON Patch (`application/json-patch+json`, RFC 6902). Помилки повертаються як `application/problem+json` з правильними кодами. Кожна операція описана в OpenAPI (короткий і повний опис, параметри, коди відповідей), дивіться Swagger UI. У Swagger і Postman авторизація через HTTP Basic тим самим логіном і паролем.

Лаба 5 (JdbcTemplate, JdbcClient). `JdbcTemplateTransactionDao` і `JdbcTemplateHouseBankDao` на JdbcTemplate, `JdbcClientPromotionDao` на JdbcClient. Обидва DAO мають CRUD, create повертає згенерований id через KeyHolder, є методи пошуку за критеріями.

Лаба 6 (Spring Data JPA). Сутності `UserAccount`, `Game`, `Bet`, `Payment` у пакеті `domain`, зв'язки один-до-багатьох користувач-ставки, гра-ставки, користувач-платежі. Репозиторії на основі `CrudRepository`. JPQL через `@Query` (наприклад `UserAccountRepository.lockById`, `BetRepository.gameStats`), через `@NamedQuery` (`Bet.findBiggestWins`), і методи, згенеровані за назвою (`findByUserIdOrderByCreatedAtDesc` та інші). Для N+1 використано `@EntityGraph`. Первинні ключі генеруються через `GENERATED ALWAYS AS IDENTITY`.

Транзакційні методи, на яких зручно показати відкат: `PaymentService.withdraw` (виведення на картку на 0119 відкотить списання), `PromotionService.activate`, `PlayService.spinSlots` / `rollDice`.
